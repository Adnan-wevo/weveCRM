# API Architecture

## Overview

The application exposes a versioned RESTful API at `/api/v1/`. Authentication uses Laravel Sanctum Bearer tokens. API documentation is auto-generated by Scribe.

## Versioning

API routes are organized under a version prefix:

```
/api/v1/auth/...
/api/v1/access-control/...
```

Central API routes are defined in `routes/api.php`. Module API routes are registered by each module's `RouteServiceProvider` under the same `/api` prefix.

## Authentication Endpoints

### Issue Token

```
POST /api/v1/auth/token
```

**Request Body** (validated by `LoginRequest`):

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `email` | string | Yes | User email address |
| `password` | string | Yes | User password |
| `device_name` | string | No | Token label (max 255 chars) |

**Success Response** (200):

```json
{
    "token": "1|abc123def456..."
}
```

**Error Response** (422):

```json
{
    "message": "The provided credentials are incorrect.",
    "errors": {
        "email": ["The provided credentials are incorrect."]
    }
}
```

### Revoke Token

```
DELETE /api/v1/auth/token
```

**Headers**: `Authorization: Bearer {token}`

**Success Response** (204): No content.

## Access Control API

All endpoints require `auth:sanctum` middleware and specific permissions.

### Users

| Method | Endpoint | Permission | Description |
|--------|----------|-----------|-------------|
| GET | `/api/v1/access-control/users` | `access-control.users.index` | List users with pagination |
| POST | `/api/v1/access-control/users` | `access-control.users.store` | Create user |
| GET | `/api/v1/access-control/users/{user}` | `access-control.users.show` | Show user details |
| PUT | `/api/v1/access-control/users/{user}` | `access-control.users.update` | Update user |
| DELETE | `/api/v1/access-control/users/{user}` | `access-control.users.destroy` | Soft-delete user |
| POST | `/api/v1/access-control/users/{user}/restore` | `access-control.users.restore` | Restore user |
| DELETE | `/api/v1/access-control/users/{user}/force` | `access-control.users.force-delete` | Permanently delete user |

**Create User Request**:

| Field | Type | Rules |
|-------|------|-------|
| `name` | string | required, max:255 |
| `email` | string | required, email, unique:users |
| `password` | string | required, min:8, confirmed |
| `password_confirmation` | string | required with password |
| `roles` | array | optional, array of existing role UUIDs |

**User Resource Response**:

```json
{
    "data": {
        "id": "uuid",
        "name": "Jane Smith",
        "email": "jane@example.com",
        "email_verified_at": "2026-02-21T00:00:00.000000Z",
        "created_at": "2026-02-21T00:00:00.000000Z",
        "updated_at": "2026-02-21T00:00:00.000000Z",
        "deleted_at": null,
        "roles": [],
        "permissions": []
    }
}
```

## API Resource Format

All API resources use consistent formatting:

- **Timestamps**: ISO 8601 format (`2026-02-21T00:00:00.000000Z`).
- **Relationships**: Conditionally loaded via `whenLoaded()`. Include relationships by eager loading in the controller.
- **Soft-Deleted Records**: The `deleted_at` field is always present (null when not deleted).
- **UUID Primary Keys**: All resource IDs are UUID v4 strings.

## Pagination

List endpoints return paginated responses using Laravel's default pagination format:

```json
{
    "data": [...],
    "links": {
        "first": "...",
        "last": "...",
        "prev": null,
        "next": "..."
    },
    "meta": {
        "current_page": 1,
        "from": 1,
        "last_page": 5,
        "per_page": 15,
        "to": 15,
        "total": 72
    }
}
```

## Filtering and Sorting

API endpoints support query parameter filtering via `abbasudo/laravel-purity`. Models with the `Filterable` and `Sortable` traits accept filter and sort parameters:

```
GET /api/v1/access-control/users?filter[name]=john&sort=-created_at
```

See `config/purity.php` for available filter operators (Equal, In, Between, Contains, StartsWith, etc.).

## Error Responses

| Status | Meaning |
|--------|---------|
| 401 | Unauthenticated (missing or invalid token) |
| 403 | Unauthorized (insufficient permissions) |
| 404 | Resource not found |
| 422 | Validation errors |
| 429 | Rate limited |
| 500 | Server error |

Validation errors follow the standard Laravel format:

```json
{
    "message": "The name field is required.",
    "errors": {
        "name": ["The name field is required."],
        "email": ["The email has already been taken."]
    }
}
```

## API Documentation (Scribe)

### Configuration

Scribe is configured in `config/scribe.php`:

- **Route matching**: `api/v1/*`
- **Auth strategy**: Bearer token
- **Try It Out**: Enabled (interactive API testing in docs)
- **Output formats**: Postman collection, OpenAPI specification

### Generation

API documentation is generated automatically during container startup. To regenerate manually:

```bash
docker exec -it wevetel_app_dev artisan scribe:generate
```

### Access

Documentation is served at `http://localhost:8000/docs`.

## Extending the API

### Adding New Endpoints

1. Create a new controller in the module's `app/Http/Controllers/` directory.
2. Create Form Request classes for validation.
3. Create API Resource classes for response formatting.
4. Register routes in the module's `routes/api.php` with `auth:sanctum` middleware.
5. Add permission checks using `$this->authorize()`.
6. Regenerate Scribe documentation.

### Adding a New API Version

1. Create `routes/api/v2.php` or a module-level equivalent.
2. Register the routes with a `v2` prefix.
3. Create new controllers/resources under a `V2` namespace.
4. Maintain backward compatibility with v1 endpoints.
